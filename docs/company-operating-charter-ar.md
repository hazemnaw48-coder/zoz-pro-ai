# ميثاق التشغيل الفعلي لشركة ZOZ Pro

**الإصدار:** 1.0  
**تاريخ المراجعة:** 3 نوفمبر 2026  
**النظام الأساسي:** Supabase-first · GitHub · Gemini  
**المالك:** صاحب حساب ZOZ Pro

هذا المستند هو مرجع التشغيل الداخلي. لا يخلط بين وجود وكيل في لوحة القيادة وبين امتلاكه صلاحية فعلية لأداة خارجية، ولا يصف المسودة بأنها منتج منشور.

## ملاحظة معمارية مهمة: مسار Vercel القديم

يحتوي المستودع على ملفات Node قديمة تعتمد على `@vercel/blob` و`@vercel/queue` ومسارات `api/queue` و`api/cron`. توثيق المستودع نفسه يصف هذا المسار بأنه سياق تاريخي، وليس مسار استوديو الإنتاج الأساسي. لذلك:

- لا تستخدم هذا المسار لتشغيل ZOZ Pro الحالي، ولا تُفعّل مفاتيح Vercel أو Queue أو Blob من أجله.
- المسار التشغيلي الحالي المعتمد لهذا المكتب هو Supabase Edge Functions + قاعدة بيانات Supabase + عامل الشركة المجدول.
- لا تحذف ملفات Vercel القديمة في تغيير شامل؛ يلزم أولاً حصر جميع الاستدعاءات والاختبارات والتأكد من عدم وجود نشر يعتمد عليها، ثم إزالة معزولة باختبارات ناجحة.
- وجود الحزم في `package.json` لا يعني أنها مطلوبة في مسار الإنتاج الحالي، لكنه يعني أن تنظيف الاعتماديات لم يكتمل بعد.

| المكوّن | الحالة المثبتة | حدود الحالة |
|---|---|---|
| مكتب الشركة | يقرأ بيانات الإنتاج عبر جلسة المالك | يعتمد على جلسة متصفح صالحة |
| الأقسام والوكلاء | 10 أقسام و10 سجلات وكلاء نشطة | النشاط لا يعني أن كل أداة متاحة للوكيل |
| محرك الاستدلال | Gemini عبر Supabase Edge Function | خاضع لحصص Google وحدود الخطة |
| عامل الشركة | مجدول كل 5 دقائق | دورة واحدة لا تعني إتمام كل الأعمال الخارجية |
| مراجعة الجودة | مراجعة مستقلة محفوظة مع المهمة | لا تغني عن اختبارات الكود أو مراجعة المالك |
| YouTube | قناتان متصلتان في دورة الإنتاج الأخيرة | لا يُفترض اتصال القناة الثالثة |
| TikTok | حسابان مسجلان/متصلان في سجل التشغيل | لا يفترض نجاح الرفع أو النشر دون نتيجة API |

| جمع الاهتمام | Edge Function v2 وجدول محمي | يلزم اختبار end-to-end ومراجعة منع الإساءة قبل الإطلاق |

**قاعدة الإثبات:** لا تسجل عملية خارجية على أنها ناجحة إلا بوجود استجابة المزود ومعرّف العملية أو رابط/ملف ناتج يمكن فتحه والتحقق منه.

## حدود تنفيذ الأدوات داخل الوكلاء حالياً

فحص سجلات الإنتاج في 3 نوفمبر 2026 أظهر:
- 10 صلاحيات وكيل مفعّلة، وكلها على Gemini بمستوى `draft`.
- سجلات Canva وGitHub وNotion وSupabase وvidIQ وRunway موصوفة بأنها `mcp_connector`، لكن لا توجد لها منح تنفيذ مفعّلة للوكلاء داخل قاعدة الشركة.
- وجود اتصال في مكتبة الأدوات أو في ChatGPT لا يمنح تلقائياً Edge Function قدرة استدعاء ذلك الموصل من الخادم.
- لذلك لا يجوز وصف الوكلاء حالياً بأنهم ينفذون عمليات Canva أو GitHub أو Notion أو Runway من تلقاء أنفسهم. يمكن تنفيذ أعمال بهذه الموصلات من جلسة ChatGPT المنفصلة، لكن هذا ليس جسراً خلفياً دائماً إلى الوكلاء.

**متطلب الإكمال:** بناء موصل خادمي مستقل لكل خدمة يحتاجه الوكيل، مع أسرار محفوظة في Supabase، وقائمة إجراءات مسموح بها، واختبار اتصال فعلي، وسجل لكل استدعاء، ومنع افتراضي للنشر أو الإنفاق. لا تفعّل صلاحية وكيل قبل وجود منفذ API فعلي واختباره.

### جسر الهاتف وFlow

- أحدث سجل للجهاز `vivo V2342` هو التطبيق `0.7.6`، وآخر نبضة في 3 نوفمبر 2026؛ قدراته المسجلة `device.health_check` فقط.
- سجل أقدم للإصدار `0.7.4` يملك `device.ui_control`، لكن آخر نبضة له كانت في 2 نوفمبر 2026، لذلك لا يُعامل كجهاز تحكم حاضر.
- وظيفة `zoz-pro-device-agent` تمنع `enable_flow_automation` صراحةً وتسمح حالياً بالتحكم المقيد في تطبيقات YouTube/TikTok الأربعة فقط.
- لذلك لا توجد حالياً قدرة مثبتة على فتح Flow وإدخال prompt وإرساله تلقائياً من الجهاز، حتى لو كان كود قديم للجسر يحتوي بقايا Flow.
- يلزم تفعيل جسر الهاتف بإصدار حديث وصلاحية واجهة مستخدم مؤكدة، ثم إضافة مسار Flow محدود النطاق يثبت أن الصفحة هي `labs.google`، ويجهز النص أولاً. أي ضغط على زر التوليد يجب أن يكون خلف موافقة مستقلة بسبب استهلاك حصص التوليد.

## 2. صلاحيات الوكلاء

### تنفيذ تلقائي مسموح
- قراءة وتحليل البيانات المتاحة من الاتصالات المختبرة.
- إعداد الأبحاث والمسودات والنصوص وخطط الإنتاج.
- إنشاء ملفات داخلية في فرع تطوير أو مساحة عمل معتمدة.
- إنشاء مهام إحالة بين الأقسام وتحديث حالات المهام.
- إجراء اختبارات لا تغيّر بيانات الإنتاج أو الجمهور.
- مراجعة الجودة وإظهار المخاطر ونقاط النقص.

### موافقة المالك مطلوبة
- دمج Pull Request إلى الفرع الرئيسي أو نشر صفحة عامة.
- نشر فيديو أو منشور أو تغيير خصوصية محتوى.
- إرسال بريد أو رسالة أو التواصل مع عميل.
- تعديل بيانات KDP أو رفع كتاب أو تغيير سعره.
- استخدام حساب خارجي أو إنشاء تفويض جديد.
- شراء أو اشتراك أو إنفاق أو أي إجراء مالي.
- حذف بيانات أو تدوير أسرار أو تغيير صلاحيات المستخدمين.
- تشغيل توليد مدفوع أو خدمة قد تستهلك رصيداً.

الموافقة على تقرير أو مهمة داخلية لا تعني تلقائياً الموافقة على أي إجراء خارجي تالٍ.

## 3. دورة المهمة القياسية

1. **استقبال:** يسجل الهدف، القسم، الوكيل، المالك، الأولوية، المخرج المطلوب، وحد التكلفة.
2. **تحقق:** يفحص النظام أن القسم والوكيل نشطان وأن الأداة المطلوبة متصلة ومصرح بها.
3. **حجز:** يحجز العامل المهمة ذرياً حتى لا ينفذها عاملان في الوقت نفسه.
4. **تنفيذ:** يرسل أقل قدر لازم من سياق العمل إلى Gemini أو الأداة الفعلية.
5. **حفظ:** يحفظ المخرج الكامل، حالة التنفيذ، النموذج، وقت البدء والانتهاء، وأي خطأ.
6. **مراجعة مستقلة:** يفحص وكيل الجودة الدقة والاكتمال والسلامة وحدود التفويض.
7. **تسليم:** يعرض النتيجة على المالك أو ينشئ إحالة داخلية مسموحاً بها.
8. **إغلاق:** لا تغلق المهمة على أنها مكتملة قبل التحقق من المخرج؛ تحفظ المهام الفاشلة أو المحجوبة مع سببها.

### حالات المهام
- `queued`: جاهزة للتنفيذ.
- `running`: محجوزة وتنفذ الآن.
- `awaiting_owner`: مخرج داخلي ينتظر مراجعة المالك أو قراراً مطلوباً.
- `completed`: اكتمل العمل المحدد وتحقق مخرجه.
- `failed`: فشل التنفيذ؛ يلزم تشخيص السبب قبل إعادة المحاولة.
- `blocked`: ينقصه اتصال أو تفويض أو مدخل أساسي.

لا تستخدم `completed` لمجرد أن النموذج أعاد نصاً أو أن طلب HTTP أُرسل.

## 4. معايير قبول أي تسليم

- المخرج موجود ويمكن فتحه، وليس وصفاً لمخرج غير موجود.
- الأرقام الفعلية مفصولة عن التوقعات والافتراضات.
- كل ادعاء عن أداة خارجية مدعوم بسجل استدعاء.
- لا توجد أسرار أو رموز وصول في HTML أو Git أو السجلات العامة.
- المهمة متوافقة مع حدود التكلفة والصلاحيات.
- مراجعة الجودة تحفظ اسم المراجع والنتيجة والدرجة والوقت.
- الإحالات الداخلية مرتبطة بالمهمة الأم ولا تتكرر بلا نهاية.
- الإجراء الخارجي، إن وجد، لا ينفذ إلا بعد موافقة منفصلة.

## 5. قواعد البيانات والأمن

- فعّل RLS على الجداول المكشوفة، وراجع المنح والسياسات معاً.
- الجداول التي لا تملك سياسات ولا منحاً للأدوار العامة تظل مغلقة؛ لا تضف سياسة عامة لمجرد إسكات فحص أمني.
- لا تضع `service_role` أو أسرار المزود في تطبيق الهاتف أو صفحات GitHub Pages.
- خزّن أسرار الخادم في Supabase Vault/Secrets فقط.
- لا تعتمد على `user_metadata` في قرارات التفويض.
- أي وظيفة `SECURITY DEFINER` يجب أن يكون لها تحقق صريح من هوية وصلاحية المستدعي، ومسار بحث ثابت.
- اختبر الوصول بمالك مصادق، ومستخدم آخر، وزائر غير مصادق.
- احتفظ بسجل للأحداث دون كتابة الرموز أو كلمات المرور أو بيانات حساسة.

## 6. سياسة التكلفة

- الميزانية الافتراضية للوكلاء: صفر.
- لا تفتح اشتراكاً أو خدمة مدفوعة ولا تتجاوز الحصة المجانية.
- عند ظهور 429 أو تجاوز حصة أو حاجة إلى بطاقة/دفع: أوقف المهمة، سجّل السبب، وقدّم بديلاً مجانياً إن أمكن.
- لا تستخدم الهاتف باعتباره خادماً يعمل 24/7؛ الجدولة يجب أن تكون على الخادم.
- لا تكرر استدعاءات النموذج تلقائياً بلا حد؛ طبّق backoff وعدداً أقصى للمحاولات.

## 9. سجل المخاطر المفتوحة عند المراجعة

1. KDP المباشر غير مهيأ؛ لا يمكن اعتبار حالة الكتب في سجل المتابعة دليلاً على مبيعات حية.
2. Google Flow لا يملك حالياً مساراً آلياً مثبتاً لإرسال المشاهد واستلامها.
3. بعض أدوات الكتالوج مسجلة كمتصلة، لكن يجب إثبات الاستدعاء لكل عملية قبل الاعتماد عليها.
4. صفحة المنتج #46 لم تُدمج بعد، وبالتالي لم تُنشر.
5. نموذج الاهتمام يستخدم وظيفة خادمية وجدولاً مغلقاً؛ يلزم استكمال اختبار إساءة الاستخدام/تحديد المعدل قبل فتحه للجمهور.
6. فحوص Supabase تعرض ملاحظات أداء وسياسات RLS مغلقة عمداً؛ لا تغيّر السياسات دون فهم مسار الوصول المقصود.
